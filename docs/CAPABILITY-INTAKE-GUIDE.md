# 管理员能力接入手册

## 1. 先判断接入类型

管理员入口为 `/admin/capabilities`，需要 `ADMIN` 角色。现行接入格式为 `Capability Manifest 2.1`，Skill 和工具使用同一份结构。

接入仍包含两件不同的事：

1. **能力登记与治理**：管理员使用 2.1 清单完成资料、交付、审核和版本登记；
2. **工具运行能力安装**：执行器、渲染器、后端服务和第三方依赖必须已经开发并部署，JSON 只能引用这些已登记能力。

上传成功不代表新算法已经安装。正式填报前必须先判断属于纯资料变更、复用已有运行模型，还是需要开发和重新部署。

## 2. 通用准备材料

Skill 和工具都应准备：

- 中文名称、唯一英文 slug、版本号；
- 一句话说明、完整说明和维护责任人；
- 适用场景、对象、项目阶段和标签；
- 输入材料、格式和准备要求；
- 输出结果、格式及其业务用途；
- 从准备到产出的关键流程；
- 质量判断标准及每项应保留的证据；
- 必须人工确认的环节；
- 不适用场景、风险和数据边界；
- 版本变更说明、手册、FAQ 或变更日志引用。

不要填写演示下载量、虚构任务数或没有验证记录的“已验证”。

## 3. Skill 与工具的差异

### 3.1 Skill

额外准备运行环境、安装方法、包内文件清单和交付包。页面当前允许选择 `.zip`、`.tar`、`.gz` 或 `.jar`。

后端依据 Manifest 判断是否必须有包，但不会替管理员逐项验证压缩包内容。建议 Skill 包至少包含 `SKILL.md`，并让 `delivery.package.packageItems` 与实际文件一致。

### 3.2 工具

额外准备：

- 在线入口是否已经接通及真实路由；
- 接受的文件类型和最大文件大小；
- 数据在浏览器、平台后端还是第三方服务处理；
- 外部服务名称；
- 文件和结果留存策略；
- 面向用户的数据告知；
- 使用的渲染器、执行方式和已登记处理器；
- 如提供本地部署，准备部署包、依赖和部署说明。

Manifest 可以登记上述信息，但不能安装运行代码。工具尚不能执行时，`delivery.online.enabled` 必须保持 `false`。

## 4. 准备 Capability Manifest 2.1

从管理页面“Schema 2.1”下载模板，或参考：

- `capabilities/platform-skill-adapter/capability.json`
- `capabilities/meeting-minutes/capability.json`

必须满足：

- `schemaVersion` 为 `2.1`；
- `kind` 为 `skill` 或 `tool`；
- `identity.slug` 只含小写字母、数字和连字符；
- 至少有一个场景、输入、输出、流程和快速上手项；
- 至少有一个质量维度、人工确认项和边界；
- Skill 有 `delivery.package`；
- 工具有 `delivery.online`；
- `hybrid` 同时有 `package` 和 `online`；
- 已开放在线工具具有可校验的 `runtime`；
- 导入只保存草稿；发布时的审核账号和日期由后台治理操作生成；
- 版本说明不为空。

后台保存的 Manifest 文本不能超过 1 MB。接入页文件选择区虽然允许不超过 2 MB，JSON 仍应控制在 1 MB 内，避免前台预检通过而后台拒绝。

### 4.1 旧格式兼容

管理页面仍能读取 `Capability Manifest 2.0` 和旧运行型 `tool.json 1.0`，并转换为统一预览。它们只用于迁移已有内容：管理员应补齐 2.1 字段并导出新清单，不要继续为新增能力编写旧格式。

## 5. 导入和预检

1. 进入 `/admin/capabilities` 的“统一接入”。
2. 选择或拖入 2.1 JSON。
3. Skill、`package` 或 `hybrid` 交付同时选择交付包。
4. 阅读结构、渲染器、处理器和数据边界检查结果。
5. 预检通过后打开统一详情预览；工具同时检查统一运行页预览。
6. 进入编辑器，补全分类、质量、边界、交付和版本说明。
7. 保存草稿后进入“版本与审核”，填写意见并提交；由未参与该版本创建、修改或提交的另一位管理员审核通过，再执行发布。

出现“平台未注册执行器”或“未登记处理器”时，必须交给开发人员实现并重新部署，不能靠修改文案绕过。

## 6. 交付包要求

- 文件名包含 slug 和版本，例如 `platform-skill-adapter-1.2.0.zip`；
- 不得包含密码、Token、生产连接串、真实业务数据或个人临时文件；
- 在手册中写清依赖、环境变量、安装步骤和卸载方法；
- Manifest 包内清单与实际文件一致；
- 上传前在批准环境中完成解压、安装和最小可用验证；
- 工具部署包说明端口、存储、外部服务、权限、超时和数据清理；
- 上传新包时同步更新版本号和变更说明。

纯在线工具的 `delivery.mode` 为 `online` 时可以不上传部署包。Skill、`package` 或 `hybrid` 没有包时，后端会拒绝保存。

## 7. 审核、发布与版本

状态包括：

- `DRAFT`：资料正在编辑；
- `IN_REVIEW`：已提交审核；审核通过后仍保留此状态，页面另显示“审核通过，待发布”；
- `PUBLISHED`：版本曾经发布，只有同时被已发布资产指向的当前版本可由公共接口读取；
- `ARCHIVED`：版本已归档，或资产已下架；页面结合资产和版本记录区分。

发布前至少确认：

- 名称、slug、版本和维护责任清楚；
- 输入输出与实际能力一致；
- 质量证据和人工确认要求可执行；
- 数据处理位置、外部服务和留存规则经过确认；
- Skill 或部署包已验证可安装；
- 工具路由、执行器或服务端处理器已真实部署；
- 统一详情和运行预览没有误导性数字和伪交互；
- 版本说明完整，后台已经记录真实审核操作，不能用手填 reviewer 代替。

已发布版本不可覆盖。修改已发布内容或替换交付包时，必须提升 `identity.version` 后重新导入。相同 slug 的能力类型不可变，不能在 Skill 和工具之间切换。

当前已提供独立治理操作、历史版本和审计。新草稿不替换当前发布版本；下架后保留历史包，归档前需先停止当前发布。接口、职责分离及尚未联调的边界见 [审核与版本流程本地交接](GOVERNANCE-DEVELOPMENT-20260905.md)。真实数据库持久化和浏览器全流程仍需测试环境验收。

## 8. 统一渲染器适用范围

### 8.1 `document-transform`

适用于单次输入 Markdown 或一个文件，结果是一个文件或 Markdown，流程统一为“选择操作—载入输入—处理—预览—下载”。

当前已注册执行器：

- `markdown-to-docx`
- `markdown-to-pdf`
- `docx-to-markdown`
- `pdf-to-markdown`

复用现有执行器不需要新增 Vue 页面，但将新的内置工具写入源码清单后仍需重新构建前端。

### 8.2 新浏览器执行器

交互相同但算法不同，例如 Excel 转 Markdown，需要开发浏览器执行函数、注册执行器、补充依赖和测试，然后重新构建前端。只新增 operation JSON 无法运行。

### 8.3 `server-job`

适用于后端异步任务、多阶段确认、长音视频、多文件批处理、模型、OCR、转写或其他外部服务。清单必须通过 `runtime.handler` 引用平台已经登记的处理器。

会议纪要生成器属于这一类，当前处理器为 `meeting-minutes-v1`。只有真实后端链路部署并完成联调后，才能把在线状态标为已接通。

## 9. 常见错误

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 无法解析 JSON | 语法错误、尾逗号或文件不是 JSON | 校验 JSON 后重新上传 |
| schemaVersion 不受支持 | 使用普通 JSON 或未知版本 | 新建内容使用 2.1；旧 2.0 仅用于迁移 |
| slug 校验失败 | 含中文、大写、空格或下划线 | 改成小写连字符形式 |
| 缺少使用或质量字段 | 数组为空或字段名错误 | 补充场景、输入、输出、流程、质量、人工确认和边界 |
| Skill 必须提供 package | 缺 package 配置或交付包 | 补配置并上传交付包 |
| 工具必须提供 online | 工具没有在线和数据边界配置 | 补充 `delivery.online` |
| 平台未注册执行器 | 引用了未实现算法 | 开发、注册、测试并重新部署 |
| 服务端处理器未登记 | `handler` 没有对应实现 | 完成后端和页面接入并登记处理器 |
| 保存时报 JSON 过大 | 后端限制为 1 MB | 删除内嵌大样例，改用引用或交付包 |
| 已发布版本不能覆盖 | 使用相同版本更新已发布记录 | 提升版本并填写变更说明 |
| 发布后公共页看不到 | 状态不是 PUBLISHED 或保存失败 | 检查状态、审核信息和后台响应 |
| 已登记但工具不能处理 | 只有 Manifest，没有运行代码或服务 | 完成运行链路开发部署 |

## 10. 迁移期注意事项

当前 7 个 2.1 源码清单分别位于 `capabilities/<slug>/capability.json`，包含五个 Skill 和两个工具。前端内置资料由 `scripts/sync_capability_catalog.py` 生成，不能手工编辑；生产默认后台模式，后台不可用或无权限时展示错误，不能恢复内置资料。清单和真实交付包尚需在目标环境逐项导入，见 [能力包开发交接](CAPABILITY-PACKAGES.md)。

旧 `skillCatalog.ts`、`skillExperience.ts`、旧工具定义和部分旧详情路由仍用于兼容。每迁移一个现有能力，都要同时验证：

1. 管理端资产列表和统一详情预览；
2. 公共能力详情接口；
3. 原 Skill 或工具入口；
4. 交付包下载；
5. 工具真实执行和数据告知。

全量迁移前不要删除兼容内容；迁移完成后也不要继续维护两份业务事实。目录说明见 [《项目目录与事实源》](PROJECT-STRUCTURE.md)。
