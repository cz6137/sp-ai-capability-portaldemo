本轮修正的三处“检查存在但从未生效”的缺陷（都属于生产代码，不是测试写法问题）：

1. 清单 `references` 是按名称索引的对象，校验却按数组遍历，导致“引用值必须是文字”和“本地引用文件必须存在”两项检查从未执行；
2. `ZipDirectoryPolicy` 原用 `ZipEntry` 读取条目类型，而 Java 8 并不提供该 API，导致链接和特殊文件检查实际为空；
3. 缺失 `packageItems` 的报错不包含文件名，管理员无法判断缺哪个文件。

现改为按字段名遍历 references，并从 ZIP 中央目录原始字节读取外部属性（文件类型位于高 16 位），同时拒绝 ZIP64 哨兵值和异常目录。上述修正在 Java 8 上实测确认。

仍属事实边界，不能据此声称已完成：

- 用真实数据库和两个真实管理员账号跑通登录、草稿、审核、发布、下架、历史包下载与审计回读（并发写锁、事务回滚仍未联调）；
- 会议纪要、文档转换真实业务回归，以及各 Skill 交付包的实际安装与最小可用验证；
- 真实服务启动。当前 `127.0.0.1:5432` 的 PostgreSQL 未连接，MongoDB 亦未确认，因此本地跑的是隔离单元测试和前端构建，不是业务后台；
- 本地预览辅助接口不实现真实保存或发布，前端显示的“未连接业务后台”提示属实。

### 历史记录维护还只有界面，数据是示例（2026-09-16）

审批工作台每行的「历史」按钮可以打开抽屉，展示该交付物的版本列表和逐版本操作记录。**抽屉里的内容全部是前端写死的示例数据，不是数据库里的真实记录**，不能作为审批、上架或下架的依据。

- 界面代码：`frontend/src/views/CapabilityApprovalView.vue`（抽屉部分标注了「示例数据」）
- 示例数据：`frontend/src/data/historyDemo.ts`，文件头写了 DEMO 声明；其中的 `HISTORY_DEMO` 常量目前没有任何地方引用

这一块**本轮不动代码**。要接真实数据必须先有数据库侧的支持，原因如下：

现有表已经能存放历史，但缺一个按资产聚合的读取方式：

| 表 | 已有什么 | 缺口 |
| --- | --- | --- |
| `capability_asset` | `status`、`current_version_id`，是“当前上架的是哪个版本”的唯一事实来源 | 无 |
| `capability_version` | 每个版本的状态、创建时间，已发布的版本不被覆盖 | 无 |
| `audit_log` | `action`、`actor_id`、`before_data`、`after_data`、`reason`、`created_at`，已记录是谁在什么时间做了什么 | `target_id` 存的是**版本 ID**，没有资产维度的聚合键 |
| `capability_package` | 版本对应的交付包 | 无 |

因此现在要“看某个能力的完整历史”，只能先列出该资产的全部版本，再逐个版本查审计记录，是 **N+1 次查询**。首版可以接受，但接口必须先定下来，不能像现在这样由前端拼。

接入时需要后端提供的能力（本轮不实现，仅记录）：

1. 资产级历史接口：输入能力标识，返回该资产的版本列表（含每个版本的状态、是否当前公开、时间）和各版本的操作记录；
2. 或者给审计记录补一个资产维度的可查询键，让一次查询就能取回某个能力的全部操作记录；
3. 上架、下架、归档、恢复都必须继续走既有状态机并写审计，历史板块只读，不提供直接改状态字段或删除记录的入口——恢复某个版本要发起一次真实操作，不能直接改 `current_version_id`。

接入真实数据时应当删除 `frontend/src/data/historyDemo.ts`，把 `historyForAsset()` 换成接口调用，并去掉界面上的示例数据告警条。

还有一个未决问题：**「重新上架」的流程没有定**。目前设想是退回待审核、再经独立管理员审核通过后上架（不提供一键复原，以免审计链断裂），但这属于产品决策，需要确认后再动状态机。

项目当前已经具备 Skill 和办公工具的统一展示框架，也已经提供文档转换和会议纪要两个工具入口。接下来的工作重点不是继续增加页面，而是把现有内容迁入后台、补齐审核管理、接通真实服务，并完成一次可回滚的正式部署。基础能力稳定后，还要开发“适应平台 Skill”，帮助管理员把外部 Skill 和工具资料整理成平台能够检查的统一格式。

## 一、本地开发人员需要完成的工作

### 1. 整理现有的六项能力

平台现在有四个 Skill 和两个办公工具。请逐项检查名称、用途、输入材料、输出结果、使用步骤、注意事项、维护人员和版本号，确保页面描述与真实能力一致。

### 2. 补齐四个 Skill 的下载包

Skill 不只是页面说明，还必须有可以交付给使用者的能力包。请确认每个 Skill 的压缩包中包含实际可用的说明、规则、模板或脚本，且压缩包内容与页面上的文件清单一致。

### 3. 把六项能力录入后台

目前前端保留了一份内置清单，用于后台尚未启动时展示页面。请通过管理员页面把六项能力逐项保存到后台数据库，并检查能力名称、版本、状态和交付包是否正确。

完成后，关闭前端兜底数据时，能力目录和详情仍应能够从后台正常读取。

### 4. 补完整的审核和发布流程

目前管理员可以录入和修改能力，但完整的审核流程还需要补齐。请增加提交审核、审核通过、退回修改、正式发布、停止发布和归档等操作，并记录是谁在什么时间进行了操作。

完成后，内容维护人员不能自行完成最终审核；普通用户只能看到已经正式发布的内容。

### 5. 补齐历史版本和操作记录

请让管理员能够查看一项能力过去发布过哪些版本、每次修改了什么、使用了哪个下载包，以及由谁审核。已经正式发布的版本不能直接覆盖，修改时必须建立新版本。

完成后，遇到内容错误时，可以查到来源，也可以确认当前页面对应哪个版本。

会议纪要页面和后端处理入口已经具备，但仍需要在安全的测试环境中接通语音转写和文本整理服务。请使用脱敏录音验证上传、转写、纪要生成、人工修改和文件下载的完整过程。

还要验证文件过大、格式不支持、网络超时、外部服务失败和用户取消等情况。只有真实处理通过后，页面才能显示为“已开放”。

完成后，文件选择、处理、预览和下载方式应保持一致；转换失败时应给出清楚提示，不能生成看似成功但内容为空的文件。

扫描版 PDF、批量转换和自定义 Word 模板不属于当前首版范围，不要为了覆盖这些情况临时增加复杂功能。

### 9. 在迁移完成后整理旧文件

在确认之前不要大规模移动或删除旧文件，也不要继续把新的业务资料写入旧文件。具体目录边界见《项目目录与事实源》。

全部检查通过后，重新构建前端和后端，生成两个新的部署文件。不要直接修改原有部署文件，也不要把整个开发目录压缩后交给部署人员。

交付时应同时提供六项能力的说明文件、四个 Skill 下载包、环境配置模板、部署说明、验收清单和每个文件的校验值。环境配置模板只写配置项名称和用途，不填写真实密码或密钥。

## 二、基础稳定后再安排的工作

下面五项工作已经讨论并确认需要保留，但不应插到首轮迁移和正式部署之前。只有前面的六项能力已经从后台稳定读取、统一页面能够正常展示、真实服务完成验证后，才开始实施。

### 11. 开发“适应平台 Skill”

这个 Skill 面向平台管理员。管理员拿到一个外部 Skill 压缩包、工具说明或代码资料后，由它读取公开说明、文件清单和配置要求，整理出平台统一说明文件的草稿，并列出缺失信息和不兼容项。

首版至少要支持两类输入：常见的 Skill 文件夹或压缩包，以及包含使用说明、启动方式和接口信息的工具资料。输出应包括统一说明文件草稿、缺失字段清单、包内文件检查结果和接入建议。

它只能做检查和转换，不能运行外部脚本、自动安装依赖、直接修改平台代码或自动发布内容。如果一个外部能力需要新的页面类型、执行方式或后端接口，应明确标记为“需要开发确认”，交给开发人员判断，不能由 Skill 自行扩展系统边界。

完成后，选择一个真实 Skill 和一个真实工具做验收。管理员应能根据输出补齐资料，并通过现有管理页面保存；同一份输入重复处理时，不应生成结构完全不同的结果。

### 12. 恢复真正的全局搜索

当前阶段不要显示名不副实的全局搜索。等后台数据来源稳定后，再建立能够同时搜索已发布 Skill、已发布工具和允许公开的交付资料的入口。

完成后，搜索结果必须来自真实后台数据，并能按名称、用途、适用场景和输入材料找到内容。未发布内容、内部配置和无权限资料不能出现在普通用户的结果中。

### 13. 建立可追溯的验证记录

平台不能只给能力加一个“已验证”标签。每次验证都需要记录验证项目、使用材料、验证人、验证时间、执行版本、结果和结论，并保留能够复核的证据位置。

完成后，只有存在有效验证记录的版本才能显示相应结论；版本发生变化后，应重新判断原验证是否仍然适用。没有证据时统一显示为待验证，不能用演示数据补足。

### 14. 建立真实的使用反馈

使用反馈需要有真实提交入口、处理责任人和状态变化，不再使用固定演示案例。反馈至少要记录使用的能力和版本、问题或效果描述、提交人、提交时间、处理结论和是否需要修改能力。

完成后，管理员能够追踪一条反馈是否已经受理和解决；普通用户只能看到经过确认、允许公开的内容，不能把内部问题或敏感材料直接展示在前台。

### 15. 评估下一批办公工具

下一批工具应从真实办公需求中选择，例如合同要点提取、材料比对或表格整理，但不要只因为 Git 上有现成项目就直接接入。先确认使用人、输入材料、输出结果、数据安全级别和维护责任，再决定是否进入平台。

完成评估时，应优先复用现有统一页面和输入、处理、结果三个阶段。只有交互确实不同且已有明确需求时，才增加新的统一渲染方式；不能每增加一个工具就单独开发一套前端。

## 三、现场部署人员需要完成的工作

### 1. 先备份现有系统

部署前先备份当前运行的前端、后端、数据库和文件存储，并记录备份时间和保存位置。在开始替换前，应确认能够使用备份恢复系统。

### 2. 检查运行环境

确认服务器上的 Java、Tomcat、PostgreSQL 和 MongoDB 版本符合部署手册，并确认磁盘空间、网络连接、数据库账号和文件存储权限正常。

如果环境条件不满足，应先记录问题并交回处理，不要直接修改程序来适应未知环境。

### 3. 填写正式环境配置

按照环境配置模板填写数据库地址、文件存储地址、登录密钥、管理员初始账号以及外部语音和文本服务配置。真实密码和密钥应放在服务器受控配置中，不应写进部署文件。

首次启动完成后，应更换默认管理员密码，并关闭仅用于初始化的设置。

### 4. 先部署后端，再部署前端

按照部署手册停止 Tomcat、备份旧文件、放入新的后端和前端部署文件，然后重新启动。不要在服务器上临时修改编译后的文件。

后端启动并通过健康检查后，再检查前端首页、登录和页面路由。

### 5. 导入并审核六项能力

使用正式管理员账号，将本地开发人员提供的六项能力逐项导入。需要下载包的 Skill 必须同时上传对应压缩包。

导入后不要直接全部发布。应由实际维护人员和审核人员核对内容，填写真实审核人和审核时间，再发布确认无误的能力。

### 6. 完成现场功能验收

使用脱敏材料检查登录、权限、能力目录、详情、下载、四种文档转换和会议纪要。普通用户不应进入管理员功能，未发布能力不应出现在公共目录。

会议纪要还要确认录音确实经过真实转写和整理，而不是固定样例；生成结果必须经过人工确认后再作为正式文件使用。

### 7. 检查数据和日志安全

确认网页、浏览器请求、日志和下载文件中没有出现密码、密钥或不必要的业务数据。检查会议录音、临时文件和处理结果是否按照说明及时清理。

发现敏感信息进入日志或页面时，应停止上线并交回修复。

### 8. 记录验收结果并保留回滚材料

对每项检查记录执行人、时间、结果和问题。严重问题未解决前不要宣布上线。

上线后继续保留旧部署文件、数据库备份、文件存储备份和原环境配置，直到新版本稳定运行并完成双方确认。

## 四、双方的责任边界

本地开发人员负责代码、能力说明、Skill 下载包、测试和正式构建结果，不直接覆盖现场正在运行的系统。

部署人员负责服务器环境、正式配置、备份、发布、数据导入和现场验收，不修改 Vue、Java、统一能力格式或 Skill 包内容。

如果现场发现必须修改代码或能力包的问题，应记录现象和复现步骤，由本地开发人员修复并重新提供版本，不在服务器上做无法追溯的临时修改。
